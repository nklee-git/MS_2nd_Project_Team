## 🎭 컨셉

2차 프로젝트 최종 발표 자체를 **롤플레이 사내 기술제안 피치**로 구성한다.
- **발표팀 = 카카오스타일 사내 NQNQ 개발자·데이터 아키텍트.** 부서마다 따로 노는 시스템(SAP + 각종 사내 스프레드시트/스크립트)을 직접 겪고 있는 실무자 입장에서, 이미 만든 PoC를 근거로 인프라 투자를 제안하는 컨셉.
- **청중 = 카카오스타일 경영진** (실제로는 심사위원/강사). 이 PoC에 예산·인프라 투자를 승인할지 말지 **의사결정권자**로서 발표를 듣는다.
- **배경 시나리오(가상)**: 지그재그가 무신사 스탠다드를 겨냥해 자사 PB 브랜드 **NQNQ**를 준비 중. 그 NQNQ 내부 개발팀이 부서간 데이터 단절과, 기존 SAP ERP에는 없는 패션 버티컬 재고 리플레니시먼트 기능의 공백을 겪다가, SAP는 그대로 둔 채 그 옆에 붙는 PoC(Power Platform/Dataverse 기반)를 직접 만들어 도입을 제안하는 상황.

## 🗺️ 발표 구조 (7단계)

1. **상황 설정 (Hook)** — "우리 팀이 매일 겪는 문제"로 시작: 재고·매출 데이터가 부서마다 흩어져 있어 승인 하나에 며칠씩 걸리는 현실을 우리 입으로 직접 제시
2. **현황 진단 (Pain Point)** — 현재 SAP ERP 분석: SAP는 핵심 재무/운영 ERP로 계속 쓰지만, 범용 ERP 특성상 패션 버티컬 특화 기능(체형·날씨 기반 수요예측, 재고 리플레니시먼트)은 빠져 있음 — 부서간 시스템이 따로 놀아 승인·협업도 수작업 의존
3. **솔루션 소개** — SAP는 그대로 두고 그 옆에 붙는 **AI 재고 리플레니시먼트 포인트 솔루션**(Power Platform/Dataverse 기반 PoC — RELEX/o9 Solutions/Blue Yonder 같은 실제 포인트 솔루션 벤더가 SAP 사용 기업에도 팔리는 것과 같은 구조). 기존 SAP를 뜯어내지 않고 병행 검증 가능하다는 점이 도입 리스크를 낮추는 핵심 근거
4. **라이브 데모 (발표의 클라이맥스)** — 품절위험 SKU 예측 → Teams Adaptive Card로 승인 요청 → 클릭 한 번으로 발주 확정. "이미 저희가 만들어서 돌리고 있는 프로토타입입니다"가 핵심 메시지 — **이 한 장면이 전체 발표의 핵심이며, 나머지 슬라이드는 이 장면의 설득력을 뒷받침하는 배경**
5. **왜 자체 구축이 아니라 Dataverse 위에 얹었나 (Build vs Buy)** — HauteLogic/K3 같은 기존 패션 버티컬 D365 addon도 검토했지만 대기업 티어 컨설팅 구축이라 우리 규모엔 안 맞았고, 완전 자체개발은 시간·리스크가 컸다는 점을 근거로 경량 addon 방향을 선택한 이유 설명 ([[17. 기술조사보고서]] 비교표 활용)
6. **비용/ROI** — 부서별 시스템을 따로 유지·연동하는 비용 대비, Dataverse 단일 저장소로 통합했을 때의 효과. 데이터로 뽑은 구체적 수치(분기별 목표 정확도 99~100%, 반품율 등)로 도입 효과 정량화
7. **클로징** — 이 PoC를 다른 부서·브랜드로 확장하는 전사 로드맵 제안. (장기적으로는 이 경험을 외부에도 제품화할 잠재력이 있다는 점을 곁들여) "이미 작동하는 증거가 있다"는 신뢰로 마무리

## 🔮 예측 검증 시나리오 — "커머스 전 과정을 예측한다"는 증거

라이브 데모(4번, 발주 승인 클릭)가 "AI 예측이 실제 액션으로 이어진다"를 보여준다면, 이 시나리오는 **"그 예측 자체가 믿을 만하다"**를 보여준다. 둘이 합쳐져야 설득력이 완성됨.

### 설계 원리
- nqnq.db의 시뮬레이션 시계는 **2026-08(현재 Y3 SS 완료, FW 시작 전)**에 멈춰 있음 → 9월 데이터가 아직 없다는 게 오히려 기회
- **2026-08-20을 "오늘"로 고정** → 모델은 2024-03-01~2026-08-20 데이터로만 학습
- 9월 한 달(~2026-09-20)의 "실제" 데이터는 기존 생성 스크립트(`generate_v4.py`류, Y3 FW 시즌·트렌드캡슐·프로모션 캘린더 규칙 그대로 적용)로 **미리 만들어두되 모델에는 숨기는 held-out 정답지**로 준비
- 발표에서: 예측 공개 → 액션 제안 → (짜잔) 실제 9월 데이터 공개 → 오차율 계산, 순서로 진행

### 발표에서의 효과
- 경영진(청중) 입장에서 가장 궁금한 건 "이 PoC의 예측을 믿을 수 있는가"인데, 이 시나리오가 바로 그 증거를 눈앞에서 만들어 보여줌
- 기존에 이미 확보한 "분기별 목표 정확도 99~100%" 수치와 자연스럽게 이어져 — 과거 3개년치 검증에 더해 "미래 한 달"도 라이브로 검증하는 구조가 됨

## 🎬 라이브 데모 시나리오 — SKU 각본 (2026-09-11 확정)

> 이 절은 위 "4번 라이브 데모"와 "🔮 예측 검증 시나리오"를 **하나의 연속된 장면**으로 묶는 구체적 각본이다. 정보가 여러 문서(21. Appservice Core model, 23. Alert & Trigger Rules, 최민 실시간 엔진 리뷰)에 흩어져 있어서, 발표 흐름만 보고 싶으면 이 절 하나만 읽으면 되게 정리했다.

**⚠️ 먼저 확인 필요 — 컷오프 불일치**: 아래 "설계 원리"엔 "2026-08-20을 오늘로 고정"이라고 돼 있는데, 실제 `generate_v4.py` 코드 상수는 `TODAY = date(2026, 8, 9)`다. 9월 실시간 데이터를 8/20 다음날부터 이어붙일 거면 이 상수부터 8/20으로 맞춰야 한다 — 최민님 확인 필요.

**주인공 SKU**: `NQ-TOP-001-M-BLK` (스퀘어라인 기본티, TOP, HERO 등급) — [[21. Core Product Categories]]·[[71. Entity Definitions & Data Dictionary]]에 이미 대표 예시로 반복 등장해서 발표 중 설명하기도 쉽다.

**각본 (5단계)**
1. **사전 시딩** (라이브 시작 직전, 1회) — 주인공 SKU의 `INVENTORY.available_qty`를 `reorder_point`보다 살짝 위(예: +3~5장)로 맞춰둠. 너무 크면 20분 안에 안 터지고, 너무 작으면 시작하자마자 터져서 "실시간으로 쌓이는 모습"을 못 보여줌
2. **라이브 스트리밍** — 최민님 실시간 엔진을 무대에서 돌려 주문이 대시보드에 실시간으로 쌓이는 걸 보여줌
3. **트리거** — 주인공 SKU가 `reorder_point` 도달 → `risk_score` 계산([[23. Alert & Trigger Rules]] 공식) → Dataverse `ReorderRecommendation` 레코드 생성 → Teams Adaptive Card 발송
4. **승인 (= 위 4번 라이브 데모)** — MD(나경)가 무대에서 클릭 한 번으로 승인
5. **예측 검증으로 전환 (= 위 🔮 절)** — 이 SKU를 포함한 9월(2026-09-01~09-20) 전체 예측치 vs 방금 만든 held-out 실측치 오차율 공개

**시딩이 확률에만 맡겨지면 안 되는 이유**: 최민님 실시간 엔진은 SKU를 완전 균등 랜덤(`random.sample`)으로 뽑는데, 공식 `generate_v4.py`는 인기도 가중치(`sku_weights`)를 반영한 추출을 쓴다. 균등 랜덤이면 무대에서 정확한 타이밍에 주인공 SKU가 안 뽑힐 위험이 있음 — 데모 전용 강제 포함 파라미터(`force_sku`) 추가를 제안함. 상세 설계는 최민님께 전달한 코드 리뷰 파일 참고.

**실행 주체**: 최민(실시간 엔진 + 시딩), 임현제(risk_score 산출), 나경(승인 클릭 + 발표 진행 + 컷오프 확인).
