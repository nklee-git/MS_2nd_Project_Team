- **아이디어 B**: ASP.NET Core MVC 대시보드도 승인이력/예측대조를 각각 독립 배포 가능한 위젯처럼 구성해서, Teams 앱 탭으로 개별 등록 가능하게 만들기
- 모듈화를 채택하면 A/B 중 하나를 고르는 것만으로는 부족하고, 모듈 경계를 어디서 끊을지·모듈간 데이터 계약을 어떻게 정의할지까지 구체화 필요

## 논의 4 — 1차 대비 "진짜" 업그레이드 포인트
1차의 핵심 문제는 AI 로직 일부가 실제로 동작하지 않았다는 것. RAG는 잘 만들었지만 리포트 생성에서 끝나고 액션으로 안 이어졌음. 여기서 나오는 차별점 후보:

- **① 검증 가능한 예측** — 1차는 더미값을 리턴해도 검증할 방법이 없는 구조였음. 2차는 [[16. PPT plan]]에 설계된 "9월 held-out 실측 대조" 덕분에 예측이 틀리면 라이브 데모에서 바로 드러남 — 명시적 세일즈 포인트로 활용
- **② RAG를 읽기전용 리포트 → 실제 액션(승인/발주)으로 연결** — 1차 RAG는 리포트를 보여주는 데서 끝났음. 2차 핵심 시나리오(예측→Dataverse→Teams 승인→발주확정)는 그 다음 단계(제안이 실제 액션으로 이어짐)까지 완성하는 것
- **③ RAG 소스 확장** — 1차는 정체불명 정책문서 몇 개가 소스였음. 2차는 이미 만들어둔 실제 정책 문서([[32. Inventory Policy]], [[33. Returns & RMA Process]], [[54. Task Types & Approval Workflow]] 등)를 인덱싱 소스로 재사용 가능
- **④ 웹 위젯 → Teams 네이티브** — 1차 RAG 챗봇은 대시보드 안 팝업 위젯에 갇혀 있었음. 2차는 Teams 안에서 로그인 없이 클릭 한 번으로 동작
- **⑤ 정적 알림 → 대화형 의사결정 코파일럿 (2026-08-27 추가, MATCH/MAI 벤치마킹)** — 1차 RAG는 "질문→리포트 생성"에서 끝나 대화가 일회성이었음. 무신사 MATCH(고객 접점마다 최적 의사결정을 연결하는 레이어)·MAI(그 위의 ReAct 기반 대화형 어시스턴트) 사례처럼, 승인 카드에 "왜 위험한지/얼마나 시켜야 하는지" 되물을 수 있는 후속 질의 레이어를 얹으면 ②(액션 연결)에서 한 단계 더 나아가 "액션으로 이어지는 대화형 코파일럿"이 됨. 기술 설계는 [[21. Appservice Core model]] 7-1절 — 코어 MVP와 분리된 독립 스트레치로만 진행

## 논의 5 — GenAI 활용처
GenAI 콘텐츠 생성(카피라이팅·룩북 이미지)은 스코프 제외 확정([[24. 기능명세서 v1]]). SCM 자동화 본체에 붙는 활용처는 별도:

- **① 예측근거 자연어 설명 생성** — "왜 이 SKU가 위험한지"를 모델 피처 기반으로 LLM이 한 문장 요약해서 Teams 카드에 붙이기
- **② 정책 Q&A 코파일럿** — 1차의 정책문서 RAG를 Teams 봇으로 부활, 소스는 이미 만든 실제 정책 문서로 교체
- **③ 반려 사유 후보 자동 제안** — 반려 시 LLM이 상황(재고/리드타임/예산)을 보고 후보를 미리 제안
- **④ 정기 자동 리포트 (pull → push 전환)** — 1차는 물어봐야 나오는 방식이었음. 2차는 주기적으로 Teams 채널에 자동 푸시

## 논의 7 — 소재·컬러 데이터로 SKU 피처 정교화 (2026-09-02 추가)
나경 개인 자료(패션 소재연구 리포트 — Acne Studios/thisisneverthat/Andar 실제 컬렉션의 소재 혼용률·톤/컬러 분석, [출처: Google Drive](https://drive.google.com/file/d/1ZHeJjDKy9qSxFGAaDoUwn3V6ugDoZSO7/view?usp=drive_link))를 참고해, 지금 `products.csv`에 없는 두 축을 SKU에 추가하는 아이디어.

> ⚠️ **저작권 주의**: 리포트 안의 실제 브랜드 제품 사진은 브랜드 소유 상업 이미지라 프로젝트 산출물(대시보드·피치덱)에 그대로 쓰면 안 됨. 가져다 쓸 것은 **분석 방법론과 데이터 패턴**(소재 혼용률 %, 톤/컬러 분류 체계)뿐 — 이건 나경이 직접 작성한 분석이라 문제없음.

**① 소재 구성(material composition) 필드 추가**
- 지금 SKU는 카테고리(TOP/OUT/PNT 등)만 있고 소재 정보가 없음. 리포트의 실제 소재 % 패턴(예: 울 85%+알파카 15%=보온성, 린넨+나일론=시원함)을 참고해 SKU별 소재 구성을 부여
- **논의 6의 "니트류 15~20℃ 판매 정점" 날씨-판매 비선형관계 근거를 카테고리명이 아니라 실제 소재 기반으로 정교화**할 수 있음 — ML 피처로 "카테고리"보다 "소재"가 날씨 민감도를 더 정확히 설명
- 실행: `products.csv`에 `material_composition` 컬럼 추가, [[74. Real-World Data Grounding (Weather & Body)]]에 소재↔계절민감도 매핑 근거로 반영

**② 톤/컬러 분류 체계**
- `products.csv`에 이미 `body_tone_code`로 **WRM/COOL/MUT**(퍼스널컬러) 태그가 있는 SKU(`NQ-CLR-*`)들이 있는데, 왜 그 컬러가 그 퍼스널컬러에 맞는지 설명이 없음
- 리포트의 톤 분석(light/bright/dark/grayish/deep) + 컬러 분석 방법론을 그대로 적용해, 컬러웨이-퍼스널컬러 매핑에 실제 컬러이론 근거를 붙일 수 있음
- 실행: [[22. SKU & Option Code System]] 또는 신규 문서에 톤/컬러 분류표 추가

**우선순위**: 발주 로직(`recommended_qty` 공식, ML 모델링)이 아직 없는 상태라 이건 그보다 급하지 않음 — 코어 완성 후 시간 남으면 착수.

## 논의 8 —⭐ K3 "Ratio Curves"를 recommended_qty에 적용 (2026-09-02 추가)
K3 Fashion 상세 기능 조사([[Brand_k3_fashion]], [[17. 기술조사보고서]] 참고) 중 **Ratio Curves**(사이즈별 배분 비율 템플릿 — 총수량이 정해지면 과거 비율로 사이즈별 수량 자동 분할)가 우리 `recommended_qty` 로직에 참고할 만함.

**배경**: NQNQ SKU 코드 체계가 이미 사이즈를 포함함([[22. SKU & Option Code System]] — `[브랜드]-[카테고리]-[체형/톤코드]-[일련번호]-[사이즈]-[컬러]`).

**적용 방식 두 가지**
- **(A) SKU(사이즈)별 독립 계산** — 지금 설계대로, risk_score·recommended_qty를 사이즈 포함 SKU 단위로 각각 계산. 단순하고 이미 설계 끝남
- **(B) K3식 비율 배분** — 스타일 단위로 총 `predicted_demand`를 먼저 계산하고, nqnq.db의 과거 실측 사이즈 분포로 비율 배분. 실무 ERP 패턴에 더 가깝지만 구현 복잡도 증가

**우선순위**: (A)로 코어 먼저 완성. 시간 남으면 (B)를 "실제 리테일 ERP(K3)의 검증된 패턴을 반영했다"는 발표 근거로 스트레치 추가 — build-vs-buy 논거에도 도움(우리도 성숙한 ERP 패턴을 알고 의도적으로 단순화했다는 인상).
