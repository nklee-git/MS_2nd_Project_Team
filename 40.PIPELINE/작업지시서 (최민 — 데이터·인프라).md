> **프론트(ASP.NET Core MVC)가 데이터를 가져올 때, Dataverse Web API를 직접 호출하게 할까요, 아니면 그 사이에 별도 C# Web API 서버를 하나 두는 걸 생각하고 계신가요?**

- 직접 호출이라면: Security Role만 잘 세팅하면 되고 추가 서버는 필요 없습니다.
- 별도 API라면: ASP.NET Core Web API인지 Azure Functions인지, 그리고 왜 그렇게 하고 싶으신지(성능/보안/로직 캡슐화 등) 이유도 같이 알려주시면 좋겠습니다 — 크로스커팅 계약(1-3절 데이터 흐름 순서)에 새 컴포넌트가 추가되는 거라 문서에 반영이 필요합니다.

## 2. `ReorderRecommendation` 스키마 확장 — Yes/No만 정해주시면 됩니다

기존에 확정된 7필드(`sku_code`/`predicted_demand`/`recommended_qty`/`risk_score`/`status`/`created_at`/`approved_by`)는 그대로 두고, 아래 4개 항목만 결정 부탁드립니다 — 대시보드를 실제로 구현하면서 필요하다고 확인된 목록입니다.

| # | 항목 | 왜 필요한가 | 결정 |
| --- | --- | --- | --- |
| 1 | `resolved_at` (DateTime) | 승인/반려 처리 시각 — "오늘 승인 건수" 같은 집계에 필요 | [ ] Yes / [ ] No |
| 2 | `rejection_reason` (Text) | 기능명세서에 이미 "Azure 인프라 롤이 Week 0에 확장 설계"로 최민님 담당으로 지정돼 있던 항목 | [ ] Yes / [ ] No |
| 3 | SKU 마스터를 별도 Dataverse 테이블로 분리 | 지금 대시보드는 `style_name`/`category_code`/`color_code`/`size`/`popularity_tier`를 CSV에서 직접 조인해서 쓰고 있습니다. Dataverse로 옮기면 SKU 테이블을 따로 두고 `ReorderRecommendation`에서 Lookup으로 참조할지, 필드를 그대로 복제해 넣을지 결정이 필요합니다 | [ ] 별도 테이블(Lookup) / [ ] 필드 복제 |
| 4 | risk_score 계산 근거(`stockout_urgency`, `popularity_weight`) 저장 여부 | 상세 드로어에서 "왜 이 점수가 나왔는지" 보여주는 용도입니다. 저장하지 않고 그때그때 계산해도 되면 스키마가 늘어나지 않습니다 | [ ] 필드로 저장 / [ ] 계산만 하고 미저장 |
