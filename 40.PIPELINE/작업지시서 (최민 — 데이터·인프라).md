## 2. `ReorderRecommendation` 스키마 확장 — Yes/No만 정해주시면 됩니다

기존에 확정된 7필드(`sku_code`/`predicted_demand`/`recommended_qty`/`risk_score`/`status`/`created_at`/`approved_by`)는 그대로 두고, 아래 4개 항목만 결정 부탁드립니다 — 대시보드를 실제로 구현하면서 필요하다고 확인된 목록입니다.

| # | 항목 | 왜 필요한가 | 결정 |
| --- | --- | --- | --- |
| 1 | `resolved_at` (DateTime) | 승인/반려 처리 시각 — "오늘 승인 건수" 같은 집계에 필요 | [ ] Yes / [ ] No |
| 2 | `rejection_reason` (Text) | 기능명세서에 이미 "Azure 인프라 롤이 Week 0에 확장 설계"로 최민님 담당으로 지정돼 있던 항목 | [ ] Yes / [ ] No |
| 3 | SKU 마스터를 별도 Dataverse 테이블로 분리 | 지금 대시보드는 `style_name`/`category_code`/`color_code`/`size`/`popularity_tier`를 CSV에서 직접 조인해서 쓰고 있습니다. Dataverse로 옮기면 SKU 테이블을 따로 두고 `ReorderRecommendation`에서 Lookup으로 참조할지, 필드를 그대로 복제해 넣을지 결정이 필요합니다 | [ ] 별도 테이블(Lookup) / [ ] 필드 복제 |
| 4 | risk_score 계산 근거(`stockout_urgency`, `popularity_weight`) 저장 여부 | 상세 드로어에서 "왜 이 점수가 나왔는지" 보여주는 용도입니다. 저장하지 않고 그때그때 계산해도 되면 스키마가 늘어나지 않습니다 | [ ] 필드로 저장 / [ ] 계산만 하고 미저장 |

## 6. 실시간 데이터 생성 — 기술명세 (신규, 2026-09-10 추가)

### 6-0. 배경
지금 대시보드(`SampleDataService`)는 앱 시작 시 CSV를 한 번만 읽어서 고정 스냅샷을 보여주는 구조입니다. "액티브하게 살아있는 대시보드"로 보이려면 주문·반품 같은 이벤트가 계속 발생하고, 그 결과로 재고·`risk_score`·재발주 추천·협업허브 알림까지 자동으로 갱신되는 체인이 필요합니다. 아래는 **1-2절 백엔드 아키텍처 결정에 종속**되는 항목이라 블로킹은 아니지만, 방향을 미리 정리해뒀습니다.

### 6-1. 실시간으로 생성해야 하는 데이터 (우선순위 순)
| # | 데이터 | 대응 테이블/엔티티 | 발생 조건 | 다운스트림 효과 |
| --- | --- | --- | --- | --- |
| 1 | 신규 주문 이벤트 | `orders` / `order_item` | 매 tick마다 N건 (SKU 가중치 기반 랜덤 선택) | `inventory.available_qty` 차감 |
| 2 | 재고 이동 이력 | `inventory_ledger` (`movement_type = 판매출고`) | 주문 발생 시 1:1 | 재고 감사 추적 |
| 3 | 반품 이벤트 | `return_request` | 카테고리별 `return_rate` 확률로 판정 | 재고 복원(`반품입고`), 반품 KPI 갱신 |
| 4 | 재발주 추천 신규 생성 | `ReorderRecommendation` (Pending) | `available_qty ≤ reorder_point` 도달 시 | 승인함(Approvals)에 새 행 등장 |
| 5 | 협업허브 알림 | `ALERT_LOG` (백로그 엔티티, [[71. Entity Definitions & Data Dictionary]] "다음 확장 대상" 5번) | 4번과 동시 발생 | 협업 허브 알림함에 실시간 카드 등장 — [[53. Virtual Team Profiles & Dashboard User Accounts]] 3-4절 프로세스 참고 |

카탈로그(제품/SKU/카테고리)·예측모델 산출물은 정적으로 두고, **트랜잭션성 데이터만** 실시간으로 흔드는 방식을 권장합니다. 이렇게 해야 실데이터 배치 전환(2절) 이후에도 같은 이벤트 파이프라인을 그대로 쓸 수 있습니다.

### 6-2. 참고해야 할 계산 규칙 (SSOT)
새로 만드는 게 아니라 **이미 확정된 공식을 그대로 재사용**하는 것이 원칙입니다.

- **재고정책 공식** ([[71. Entity Definitions & Data Dictionary]] INVENTORY절, `generate_v4.py`) — 분기별 판매속도(velocity) × 인기도 티어 비율 × 리드타임(52일) × 버퍼 계수로 매일 재계산:
  - `reorder_point = velocity × tier_ratio × 52 × 1.3`
  - `par_level = velocity × tier_ratio × 52 × 3.0`
  - `safety_stock = reorder_point × 0.5`
- **SKU 선택 가중치** (`generate_v4.py` 시뮬레이션 루프) — 실시간 주문이 어떤 SKU에 쏠릴지 현실감 있게 하려면 그대로 참고: 날씨(카테고리별 계절 가중치) × 사이즈 분포 × 인기도 티어(`TIER_WEIGHT`: HERO 3.0 / STEADY 1.0 / NICHE 0.3, 롱테일 반영).
- **카테고리별 반품율** (`generate_v4.py` `CATEGORIES` 딕셔너리): TOP 15% / PNT 20% / CLR 10% / OUT 18% / ACC 8% / DRS 15%.
- **트렌드캡슐 자동재발주 제외 원칙** — `line_type = TREND`인 SKU는 재발주 트리거 대상에서 제외 (소량 정예 운영 원칙, [[24. SKU Scale & Growth Roadmap]] 참고).

> ⚠️ **확인 필요 — `risk_score` 공식이 문서마다 다릅니다.**
> - [[23. Alert & Trigger Rules]] (2026-08-26 확정본): `risk_score = 재고소진임박도 × 인기도가중치`, 인기도가중치는 **고정값**(HERO 1.5 / STEADY 1.0 / NICHE 0.7).
> - 현재 대시보드 구현(`SampleDataService.BuildReorderRecommendations`, React `mockData.js` 이식본): 인기도가중치를 티어별 **랜덤 구간**(HERO 0.8~1.0 / STEADY 0.5~0.8 / NICHE 0.2~0.5)에서 뽑는 방식이라 23번 문서 공식과 다릅니다.
> - 실시간 생성부터는 이 둘 중 하나로 통일해야 승인함 필터/정렬이 일관됩니다. 아래 6-5 결정사항에 포함해뒀습니다.

### 6-3. 실행 아키텍처 (1-2절 결정에 종속)
| 방식 | 구조 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. Power Automate 스케줄 Cloud Flow | 예: 5분 주기 트리거 → Dataverse Web API로 직접 insert/update | 별도 서버·배포 불필요, 로우코드라 유지보수 쉬움 | 복잡한 랜덤/가중치 로직을 Power Automate 표현식으로 짜야 해서 `generate_v4.py` 로직 이식이 번거로움 |
| B. 별도 C# 백그라운드 서비스 (`IHostedService`/`PeriodicTimer`) | ASP.NET Core 서버(또는 Azure Functions Timer Trigger) 안에서 주기 실행 → Dataverse Web API write | `generate_v4.py`의 가중치·공식 로직을 C#으로 그대로 포팅 가능, 테스트하기 쉬움 | 1-2절에서 "별도 API 서버"로 결정될 때만 자연스럽게 얹을 수 있음 |

1-2절에서 "직접 호출"로 결정되면 A, "별도 API 서버"로 결정되면 B가 자연스러운 선택지입니다.
