## 1. 승인이력 뷰

### 1-1. 요약 카드 (화면 상단, 4개)
| 카드 | 계산 방식 |
| --- | --- |
| 대기중 발주추천 | `status = Pending`인 레코드 수 |
| 오늘 승인 건수 | `status = Approved` AND `created_at`이 오늘 |
| 반려율 | `Rejected` / (`Approved` + `Rejected`) × 100 |
| 평균 처리시간 | `created_at` ~ 승인/반려 시점까지 평균 |

### 1-2. 필터/검색/정렬 바
- **상태 필터**: 전체 / 대기 / 승인 / 반려 (칩 형태, 다중 선택 아님)
- **카테고리 필터**: TOP/PNT/OUT/DRS/CLR/ACC (드롭다운, `products.category_code` 기준)
- **인기도 필터**: HERO/STEADY/NICHE (`products.popularity_tier` 기준)
- **검색**: SKU 코드로 검색 (`sku_master.sku_code` 부분 일치)
- **정렬**: risk_score 내림차순(기본) / 생성일시 / 추천수량 — 컬럼 헤더 클릭으로 전환

### 1-3. 발주추천 테이블
| 컬럼 | 데이터 출처 | 표시 방식 |
| --- | --- | --- |
| SKU | `ReorderRecommendation.sku_code` | 코드 그대로(모노스페이스 폰트) |
| 스타일명 | `products.style_name` (sku_code로 조인) | 텍스트 |
| 카테고리/컬러/사이즈 | `products.category_code`, `sku_master.color_code`, `sku_master.size` | 뱃지 3개 나열 |
| 인기도 | `products.popularity_tier` | 뱃지 (HERO=강조색, STEADY=중립, NICHE=연한색) |
| risk_score | `ReorderRecommendation.risk_score` | 숫자 + 가로 바(0~1 그라데이션, 색상은 위험할수록 진하게) |
| 예측수요 | `ReorderRecommendation.predicted_demand` | 숫자 |
| 추천수량 | `ReorderRecommendation.recommended_qty` | 숫자 |
| 상태 | `ReorderRecommendation.status` | 뱃지(대기=amber/승인=green/반려=red) |
| 생성일시 | `ReorderRecommendation.created_at` | 상대시간("3시간 전") + 툴팁에 절대시각 |

- 페이지당 20건, 페이지네이션(또는 무한스크롤 — 구현 편한 쪽으로 최종 선택)
- 빈 상태: "대기중인 발주추천이 없습니다" 안내 문구 + 아이콘

### 1-4. 상세 드로어 (행 클릭 시)
우측에서 슬라이드로 열리는 패널. 목록 화면을 벗어나지 않고 근거를 확인 → 바로 승인/반려까지 하는 게 목적.
- **risk_score 산출 근거 분해**: 재고소진임박도 × 인기도가중치 — 각 항목 숫자와 함께 막대로 시각화 ([[23. Alert & Trigger Rules]] 공식 그대로)
- **재고 현황 바**: `available_qty` / `reserved_qty` / `safety_stock` / `reorder_point`를 한 눈에 비교하는 가로 스택 바
- **최근 판매 추이 미니차트**: 해당 SKU의 최근 N일 판매량 스파크라인
- **승인/반려 버튼**: 승인 클릭 시 `status → Approved`, `approved_by` 기록. 반려 시 사유 입력 필드(자유 텍스트) — 자동 제안은 [[19. 데모 시나리오 후보 (초안)]] 시나리오 9(RAG 스트레치)라 지금은 자유입력만
  > 2026-09-09 추가: 반려 사유 입력에 PART 2(3-2절) 해시태그 칩 5종이 함께 붙었습니다.

## 2. 예측대조 뷰

### 2-1. 요약 카드 (3개)
| 카드 | 계산 방식 |
| --- | --- |
| 검증 기간 | cutoff(8/20) ~ held-out 종료일 |
| 평균 오차율(MAPE) | \|예측값-실측값\|/실측값의 평균 |
| 목표 정확도 대비 달성률 | [[44. KPI Definitions]]의 분기별 목표 정확도와 비교 |

### 2-2. 기간 선택기
- 프리셋 버튼(최근 7일 / 전체 held-out 기간) + 커스텀 날짜 범위

### 2-3. 메인 예측-실측 라인차트
- X축: 날짜, Y축: 수요량(개)
- 실선 = 실측, 점선 = 예측 (색상 구분)
- 카테고리 필터 토글(전체 보기 / TOP·PNT·OUT·DRS·CLR·ACC 개별 보기) — `category_code`별 집계

### 2-4. 카테고리별 오차율 바차트
- 6개 카테고리(TOP/PNT/OUT/DRS/CLR/ACC) 각각의 오차율을 막대로 비교
- **패션 도메인 포인트**: 카테고리별 계절 민감도([[74. Real-World Data Grounding (Weather & Body)]] — OUT은 추울수록↑, DRS는 따뜻할수록↑)가 실제로 오차율에 반영되는지 보여주면, "왜 이 카테고리는 유독 잘 맞았는지" 설명 근거가 됨 → 발표에서 패션 도메인 지식으로 설명할 수 있는 포인트

### 2-5. SKU별 오차 상세 테이블
- 오차 큰 순서로 정렬, "이 SKU가 몇 % 벗어났는지" 리스트
- 행 클릭 시 해당 SKU만 메인 차트에 하이라이트

## 3. 데이터 조회 뷰 (Should)
> 근거: 무신사 데이터플랫폼팀이 사내 쿼리 조회 프로그램을 배포한 뒤 실사용률이 꾸준히 늘고 있고, 관련 교육도 계속한다는 벤치마킹 사례 참고(PM 제공). "매번 엑셀로 내려받는" 방식보다 자체 조회 도구가 있는 게 이 프로젝트의 핵심 목표(의사결정 단축·자동화)와도 맞음.

### 3-1. 왜 자유입력 SQL이 아니라 "질문 칩"인가
완전 자유 텍스트 질의(자연어→SQL 자동생성)는 지금 단계엔 안전장치 없이 넣기엔 위험함(잘못된/의도치 않은 쿼리 생성 가능) — 대신 **미리 정의한 질문 몇 개를 버튼(칩)으로 눌러서 결과를 보여주는** 방식으로 시작. "AI 에이전트가 도와준다"는 느낌은 유지하면서 안전하고 개발 비용도 낮음.

### 3-2. 질문 칩 후보 (실제 데이터로 답 가능한 것만)
| 질문 칩 | 내부적으로 하는 일 |
| --- | --- |
| "이번 주 반품 많은 카테고리는?" | `returns` 테이블을 카테고리별 집계 |
| "가장 위험한 SKU 5개는?" | `ReorderRecommendation`을 risk_score 내림차순 정렬 후 상위 5개 |
| "이번 달 채널별 매출은?" | `orders.channel_id` × `monthly_revenue_summary` 집계 |
| "인기도 티어별 평균 판매량은?" | `popularity_tier_performance` 조회 |

### 3-3. 화면 구성
- 질문 칩 4~6개 버튼으로 나열(자유입력 검색창은 이번엔 넣지 않음)
- 클릭하면 표 또는 간단한 차트로 결과 표시(질문 성격에 따라 자동 선택)
- "결과 다운로드(CSV)" 버튼 — 기존 "엑셀로 내려받기" 습관을 그대로 대체

| 차트 라이브러리 후보 | Recharts 또는 Chart.js | Recharts |

### 4-1. 컬러 팔레트 (2026-09-09 확정)
지그재그 기술팀이 만든 것처럼 느껴지도록, 실측한 지그재그 브랜드 핑크 계열로 전면 교체:
